# Restyling a .pptx onto this system

A deck that already exists usually arrives as loose text boxes with no master —
generated by python-pptx, or built by hand. Rebuilding it on a template master
means repositioning every shape blind. Swapping the tokens and the page furniture
gets most of the identity for a fraction of the risk, so start there and only
reflow when you can actually see the result.

## Token map

Whatever palette the deck arrives with, map it onto the system rather than
inventing new values:

| Role in the source | Becomes |
|---|---|
| heading / emphasis colour | Navy `#14243F` |
| body text | Ink `#2B2F36` |
| secondary, captions | Muted `#6B7280` |
| "positive result" colour | Teal `#0EA79A` |
| panel / table fill | Surface `#F6F7F9` |
| any second accent | Teal, or drop it |

Then set every run to Archivo (Pretendard as the East-Asian font if the deck has
Korean), replace the title rule with the teal-capped divider, add the footer
lockup, and rebuild the cover.

**Placeholder markers are not part of the palette.** Decks in progress often mark
"data goes here" with a red dashed box. Leave those red — recolouring them to a
brand colour makes an unfilled slot look like a finished design, and someone will
present it that way. Only recolour red that is being used for ordinary emphasis.

## The python-pptx border trap

Reading `shape.line.color` **creates** an `<a:ln>` element as a side effect —
`LineFormat.fill` calls `_get_or_add_ln()`. The result is
`<a:ln><a:solidFill/></a:ln>`, a solid fill with no colour, which PowerPoint
renders as a black outline. Merely checking whether a shape has a line colour
therefore draws a border on every text box in the deck.

Read line colour off the XML instead:

```python
from pptx.oxml.ns import qn

def existing_line_colour(shape):
    spPr = shape._element.find(qn("p:spPr"))
    if spPr is None:
        return None, None
    ln = spPr.find(qn("a:ln"))
    if ln is None:
        return None, None
    clr = ln.find(qn("a:solidFill") + "/" + qn("a:srgbClr"))
    return ln, (clr.get("val", "").upper() if clr is not None else None)
```

Verify afterwards — the count of `<a:ln>` elements should not jump, and none
should hold an empty `<a:solidFill/>`:

```bash
python3 - <<'PY'
import zipfile, re
z = zipfile.ZipFile("out.pptx")
for n in z.namelist():
    if n.startswith("ppt/slides/slide") and n.endswith(".xml"):
        s = z.read(n).decode()
        assert not re.search(r"<a:ln[^>]*>\s*<a:solidFill/>\s*</a:ln>", s), n
print("no empty line fills")
PY
```

Two more python-pptx notes: assigning `text_frame.text` collapses a paragraph to
one unstyled run, so assign `run.text`; and it cannot duplicate a slide.

## Embedding the fonts

Recipients rarely have Archivo or Pretendard installed, so a deck that will be
presented elsewhere should carry them.

**PowerPoint embeds TrueType only.** Pretendard ships as `.otf` with CFF
outlines, which PowerPoint refuses. Convert first:

```bash
python3 scripts/otf2ttf.py Pretendard-Regular.otf Pretendard-Regular.ttf
```

Then embed. `scripts/embed_fonts.py` does the whole package job — writes
`ppt/fonts/fontN.fntdata`, adds the `fntdata` content-type default, wires the
relationships, and inserts `<p:embeddedFontLst>` in its schema position (after
`notesSz`, before `defaultTextStyle`):

```bash
python3 scripts/embed_fonts.py in.pptx out.pptx ./fonts
```

Only four slots exist per family — `regular`, `bold`, `italic`, `boldItalic` —
so pick the four weights that matter rather than embedding the full range. The
script sets `saveSubsetFonts="0"`, embedding complete fonts: a used-characters
subset is smaller but breaks the moment the recipient edits the text.

Check the result end to end — each slot's relationship should resolve to a part
whose internal family name matches the `typeface` attribute, with `fsType=0`
(OFL fonts permit embedding).

Worth telling the user: embedded fonts work reliably in PowerPoint for Windows;
Mac support depends on version, and Keynote and Google Slides ignore them
entirely. Export a PDF when the destination is uncertain.

## Checking fit without a renderer

LibreOffice is often unavailable or broken, and Archivo sets wider than the
Helvetica/Arial a draft was built in — so titles that fit before may now wrap
into the divider. `scripts/qa_fit.py` measures wrapped line counts against the
real Archivo advance widths and reports text taller than its box, shapes off the
slide, and overlapping text boxes:

```bash
python3 scripts/qa_fit.py deck.pptx
```

When a title no longer fits, drop the title size for the **whole deck** rather
than only the offending slides — mixed title sizes read as a mistake, one long
title does not.

Run the baseline against the original file too. It separates defects you
introduced from defects the draft already had, which is the difference between a
fix and an apology.

## What must survive

Confirm these explicitly before handing the file back:

- **Speaker notes** on every slide
- **Numbers, framework names, and terminology** — never "fix" a figure that looks
  wrong; ask
- **Placeholder shapes** — repositioning is fine, deleting or merging is not
- **Text content**, byte for byte, outside slides you deliberately rebuilt.
  `markitdown deck.pptx` before and after gives a clean diff.
