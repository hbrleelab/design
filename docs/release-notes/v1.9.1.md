## v1.9.1 — PowerPoint 열기 실패 수정 · Fixes a deck PowerPoint refused to open

**v1.9 의 `hbrlrg-slides.pptx` 를 받으신 분은 이 버전으로 다시 받아 주세요.**
v1.9 의 워드 파일 4종도 같은 종류의 결함이 있어 함께 고쳤습니다.

If you downloaded `hbrlrg-slides.pptx` from v1.9, replace it with this one. The
four Word files from v1.9 carried a defect of the same kind and are also fixed.

### 원인 · Cause

v1.9 에서 한글 서체(Pretendard)를 임베드하면서 `ppt/presentation.xml` 에
`charset="129"` 를 썼습니다. 129 는 윈도의 한글 charset 번호가 맞지만, 이 속성의
타입은 ISO/IEC 29500 에서 **`xsd:byte`(부호 있는 1바이트, −128…127)** 입니다.
129 는 범위를 벗어나 파일이 규격에 어긋나고, PowerPoint 는 그런 파일을 열지 않고
'프레젠테이션 복구'를 제안합니다. 올바른 값은 **`-127`** 입니다.

v1.9 embedded Pretendard with `charset="129"`. 129 is indeed the Windows charset
id for Hangul, but the attribute is typed **`xsd:byte`** — signed, −128…127 — so
the value is out of range, the part fails schema validation, and PowerPoint
offers to repair the file instead of opening it. The correct value is **`-127`**.

워드 파일에서는 별개의 같은 종류 결함이 있었습니다. 임베드 설정
(`w:embedTrueTypeFonts`)을 `word/settings.xml` 맨 앞에 넣었는데, `CT_Settings`
는 순서가 정해진 시퀀스라 `w:zoom` 이 제자리를 벗어났습니다. 규격 순서대로
넣도록 고쳤습니다. (워드가 관대해 열리기는 했으나 규격 위반은 위반입니다.)

In the Word files, `w:embedTrueTypeFonts` had been inserted at the top of
`word/settings.xml`, but `CT_Settings` is an ordered sequence, so `w:zoom` ended
up out of position. Now inserted in its declared place.

### 보고된 진단에 대해 · On the reported diagnosis

접수된 보고는 "`.fntdata` 가 난독화(EOT) 형식이 아니라 TTF 원본이라서" 라고
보았으나, 이 부분은 사실과 다릅니다. **PresentationML 의 `.fntdata` 는 원본 폰트를
그대로 담는 것이 규격입니다.** 난독화는 워드(`.odttf`)에만 적용되며, 복호화 키를
담는 `w:fontKey` 속성이 필요합니다. PresentationML 스키마(`CT_EmbeddedFontDataId`)
에는 그런 속성이 아예 없어, 난독화된 데이터를 넣으면 오히려 열리지 않습니다.
원본 TTF 를 담는 것은 정상이며, 문제는 위의 `charset` 값이었습니다.

The report attributed the failure to `.fntdata` holding raw TTF rather than an
obfuscated form. That part is not correct: in PresentationML, `.fntdata` holds
the raw font by design. Obfuscation applies only to Word's `.odttf`, and needs a
`w:fontKey` to undo — an attribute PresentationML's `CT_EmbeddedFontDataId` does
not have. Storing raw TTF is right; the `charset` value was the fault.
